# ADR 0001: Модульный монолит для MVP

- Статус: принято как архитектурная основа плана
- Дата: 2026-09-23

## Контекст

Нужно быстро выпустить MVP платформы в Москве, сохранив возможность расширить каталог, географию и нагрузку. На старте важнее скорость изменения сквозных сценариев заказа, оплаты и модерации, чем независимое масштабирование отдельных доменов.

## Решение

Начать с модульного монолита: один Python backend и одна PostgreSQL, разделённые по доменам. API, Telegram webhook/bot и фоновые workers запускаются отдельными процессами/контейнерами, используют общие доменные модули и явные интерфейсы. React Mini App — отдельное приложение.

Доменные модули: accounts, catalog, profiles, orders, chat, payments, files, moderation, notifications, admin. Межмодульные изменения выполняются через application services и доменные события/outbox, без прямого доступа к чужим таблицам из handler-ов.

## Последствия

- Быстрее разработка и локальный запуск; проще транзакционно согласовать заказ и платёжный журнал.
- Нужны модульные границы и запрет обходить application layer, иначе монолит станет связным.
- Redis/очередь и outbox готовят фоновые процессы к масштабированию.
- Выделять сервисы только при подтверждённой нагрузке, независимом цикле релизов или отдельной необходимости в надёжности.
